1. Resource Monitors devuelve "Page not found"

P0 — antes del evento
Bloquea: H25, H29 · Afecta a cualquier perfil de usuario, no solo no técnicos
Evidencia
En la sesión de browser, Admin > Cost Management > Resource Monitors devuelve "Page not found" de forma reproducible, tanto navegando por URL directa como haciendo clic desde el menú lateral (esto último descarta que sea solo un problema de "refresh").
Causa raíz confirmada

No es un problema de datos ni de permisos. Verificación vía SQL directa (rol ACCOUNTADMIN, sin pasar por la UI):

SHOW RESOURCE MONITORS;
Resultado: existen 2 resource monitors, ambos bien configurados:
MONITOR_CREDIBANCO — credit_quota=100, notify_at 75%/90%, frequency MONTHLY
RM_HOL_CREDIBANCO — credit_quota=100, notify_at 75%/90%, frequency MONTHLY (coincide exactamente con lo que promete el deck para H25/H29)

Conclusión: es un bug de routing/SPA de Snowsight en esta build, no algo que se arregle regenerando el HOL ni cambiando permisos.

Fix recomendado (pasos)
  1. Reproducir el error en una ventana de incógnito / sesión nueva, para descartar caché de browser como causa.
  2. Reproducir explícitamente con el rol ACCOUNTADMIN ya seleccionado (no con el default actual) para descartar que sea un tema de rol.
  3. Abrir la consola de desarrollador (F12) al momento del error y capturar la URL exacta que falla (ej. algo como .../resource_monitors?preset=...) y el mensaje de red/consola — esto es lo que necesita soporte de Snowflake para diagnosticar.
  4. Si persiste, abrir un caso de soporte / reportarlo al equipo de Snowsight, referenciando: cuenta otc03722 (región us-east-1, alias LEDZYD), página Cost Management > Resource Monitors, error "Page not found" reproducible por menú y por URL.
  5. Plan B para el día del evento si no se resuelve a tiempo: tener listo un worksheet con SHOW RESOURCE MONITORS; para mostrar los thresholds 75%/90%/100% vía SQL como respaldo de H25/H29, y avisar al facilitador de antemano.
Cómo verificar que quedó resuelto

Navegar a Admin > Cost Management > Resource Monitors desde el menú lateral (no por URL pegada) y confirmar que se listan MONITOR_CREDIBANCO y RM_HOL_CREDIBANCO con sus thresholds visibles en la UI, no solo por SQL.

2. Rol default incorrecto en la cuenta LEDZYD

P0 — ✅ RESUELTO
Afecta el primer minuto de cualquier evaluación en esta cuenta específica
Estado
✅ CORREGIDO: Se ejecutó ALTER USER "USER" SET DEFAULT_ROLE = ACCOUNTADMIN; en la cuenta LEDZYD el 2026-09-26. Verificado con DESCRIBE USER "USER"; — DEFAULT_ROLE = ACCOUNTADMIN.
Evidencia original
Al iniciar sesión en credibanco-hol (LEDZYD), el rol activo por defecto era OPENFLOW_ADMIN_RL (residuo de pruebas Openflow). Las otras 8 cuentas están correctas con CRB_HOL_ADMIN o ACCOUNTADMIN.
Fix aplicado
USE ROLE ACCOUNTADMIN;
ALTER USER "USER" SET DEFAULT_ROLE = ACCOUNTADMIN;
Nota sobre Openflow

Para acceder a la UI de Openflow, el usuario debe cambiar temporalmente su default role:

-- ANTES de entrar a Openflow:
USE ROLE ACCOUNTADMIN;
ALTER USER USER SET DEFAULT_ROLE = 'OPENFLOW_ADMIN_RL';
-- Cerrar sesión y volver a entrar → ir a Ingestion > Openflow

-- AL TERMINAR, restaurar:
ALTER USER USER SET DEFAULT_ROLE = 'ACCOUNTADMIN';
-- Cerrar sesión y volver a entrar

3. Data Metric Function sin resultados recientes (H05)

P0 — ✅ RESUELTO
Afecta: Data Quality tab de PAGOS.AUTORIZACIONES
Evidencia original
El Data Quality tab de PAGOS.AUTORIZACIONES mostraba "0/1 association passing" y "1 with no checks". El DMF estaba asociado pero sin evaluaciones.
Estado
✅ CORREGIDO: DMF re-asociado con TRIGGER_ON_CHANGES + DML forzado en las 9 cuentas. Evaluaciones confirmadas en LEDZYD: 18:15, 18:20, 18:25, 18:31, 18:35 — resultado consistente: 781 filas con monto inválido.
Causa raíz

El schedule original era 60 MINUTES — demasiado largo para que evaluara antes del evento. Además, TRIGGER_ON_CHANGES no dispara sin un DML real sobre la tabla.

Fix aplicado (SQL ejecutado en 9 cuentas)
USE ROLE ACCOUNTADMIN;
USE WAREHOUSE CREDIBANCO_HOL_WH;
USE DATABASE CREDIBANCO_HOL;

-- 1. Remover asociación anterior
ALTER TABLE PAGOS.AUTORIZACIONES DROP DATA METRIC FUNCTION GOBIERNO.DMF_MONTO_VALIDO ON (MONTO);

-- 2. Cambiar a TRIGGER_ON_CHANGES para evaluación inmediata
ALTER TABLE PAGOS.AUTORIZACIONES SET DATA_METRIC_SCHEDULE = 'TRIGGER_ON_CHANGES';

-- 3. Re-asociar el DMF
ALTER TABLE PAGOS.AUTORIZACIONES ADD DATA METRIC FUNCTION GOBIERNO.DMF_MONTO_VALIDO ON (MONTO);

-- 4. Forzar DML para disparar la evaluación
INSERT INTO PAGOS.AUTORIZACIONES VALUES (999998,1,1,'4111111111111111','5411','Bogota',CURRENT_TIMESTAMP(),100,'00','POS');
DELETE FROM PAGOS.AUTORIZACIONES WHERE AUTORIZACION_ID = 999998;
Verificación
SELECT MEASUREMENT_TIME, VALUE, METRIC_NAME 
FROM SNOWFLAKE.LOCAL.DATA_QUALITY_MONITORING_RESULTS 
WHERE TABLE_NAME = 'AUTORIZACIONES' 
ORDER BY MEASUREMENT_TIME DESC LIMIT 3;
-- Debe mostrar evaluaciones recientes con VALUE = 781
Cómo verificar en la UI

Catalog > Explorer > PAGOS > AUTORIZACIONES > Data Quality tab → debe mostrar "1/1 association passing" con resultado 781. Si muestra caché viejo, cerrar y reabrir el tab.

8. Reautenticación OAuth al abrir apps Streamlit desde "Apps"

P1 — importante
Afecta: H17, H18, H26 · Descubierto en el cierre final del re-test (ronda 3)
Evidencia
Al hacer clic en un Streamlit app instalado desde Apps (ej. DASHBOARD_BI_CREDIBANCO), Snowsight redirige a una pantalla completa de login OAuth ("Sign in to Snowflake") pidiendo usuario/contraseña de nuevo, en vez de abrir directo con la sesión ya activa. Confirmado reproducible: pasó también al abrir DASHBOARD_MLOPS desde el mismo catálogo de Apps.
Causa raíz

Los Streamlit apps corren en un dominio/flujo OAuth separado (parámetros de URL observados: source=streamlit&interface=streamlit). No es un fallo de la sesión — es un segundo flujo de autenticación legítimo pero no anunciado al usuario.

Impacto en la evaluación de Maria

Una usuaria no técnica puede interpretar la pantalla de login como "se cerró mi sesión" o un error de la plataforma, generando desconfianza justo antes de ver el dashboard de negocio (H17/H18/H26), que es contenido de alto impacto para el evento.

Fix recomendado
  1. Agregar una nota explícita en guia_participante_v4.html y en credibanco_overview_deck.html (tarjetas H17, H18, H26): "Al abrir esta app puede pedirte iniciar sesión otra vez — usa las mismas credenciales, es normal."
  2. Reportar al equipo de producto de Snowsight si existe una forma de propagar la sesión ya activa a los Streamlit apps sin un segundo login (SSO interno), para eliminar la fricción de raíz.
Cómo verificar que quedó resuelto

Confirmar que la nota está en la guía y el deck, o que el segundo login ya no aparece (si se resuelve del lado de producto).

9. Clic directo en la fila de un Resource Monitor da "Page not found"

P1 — importante
Afecta: H29 · Refina el Fix 1 (la lista general ya funciona; el detalle individual no)
Evidencia
En Admin > Cost Management > Resource Monitors, la lista carga bien ("2 Resource Monitors"). Pero hacer clic en el nombre de la fila — el comportamiento intuitivo, reforzado por un header de columna literalmente llamado "Row click action" — navega a /#/account/usage/resource_monitors/MONITOR_CREDIBANCO y devuelve "Page not found", incluso después de refrescar la página (a diferencia del Fix 1 original, este no se arregla con refresh).

El menú "..." (Actions) → "Edit" junto a la fila SÍ abre un modal funcional "Edit Resource Monitor" que muestra Credit Quota (100.00), Schedule (Start Monitoring, Resets Monthly) y la sección Actions con los 3 umbrales de notificación: 100% (Suspend + notify), 75% (Notify), 90% (Notify) — coincide exactamente con lo que promete el deck para H29.

Cómo verificar que quedó resuelto

Hacer clic directo en el nombre de MONITOR_CREDIBANCO desde la lista y confirmar que ya no da "Page not found", sino que abre una vista de detalle válida.
